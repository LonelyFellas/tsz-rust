# 后端评估：定档 → 调研 → spec → 交接

本文件是 Claude Code 下后端 assess 的**唯一**流程来源，自带完整规则。
项目约定读 `AGENTS.md` 与仓库文档。**本技能不写实现代码、不跑迁移、不改数据库。**

## 1. 先定档

| 档位     | 判据                                                                             | 产出                                        |
| -------- | -------------------------------------------------------------------------------- | ------------------------------------------- |
| **跳过** | 一句话能说清 diff：改日志、重命名、补一条断言、调整错误文案                      | 不写文档，直接进 [build](../build/SKILL.md) |
| **轻档** | 单模块内、不动 DTO / 迁移 / OpenAPI / 权限                                       | 一份 `design.md`，**≤80 行**                |
| **重档** | API 契约变更、数据库迁移、跨模块、鉴权/权限、数据约束变化、**需要前端配套发布**  | `requirements.md` + `design.md`             |

按兼容性、数据与权限风险定档；纯文案等变化不因前端可见而自动升档。定档说明理由。

## 2. 建立基线

小范围调查由当前 agent 完成；存在可独立并行的调查且收益明确时使用只读子代理。
按 handler → DTO → service → repository → 数据约束核对必要调用链。涉及 API/DTO 时核对前端实际消费者，复用已有证据。

## 3. spec 必须写清发布顺序

写入 `docs/features/<slug>/`；跨仓功能的 spec 集中在任务主仓（通常是前端 tsz），本仓引用即可。

`design.md` 除常规内容（要改的文件与签名、范围外、方案与被否决方案、风险与回退）外，
**后端必须额外写清三件事**：

1. **迁移** —— up/down 成对、执行顺序、对历史数据的影响、能否回退。
2. **契约影响** —— 哪些 method/path 的请求或响应形状变了，字段的必填/可选/nullable/枚举变化。
3. **发布顺序** —— 仅涉及配套发布时，按实际 schema 与消费者验证新旧组合；使用本仓 `.agents/skills/contract-sync/SKILL.md` 及配套发布清单。
   不按字段新增/删除硬编码顺序，兼容性未知时补验证或兼容方案，不写「同批发布」来代替验证。

## 4. 验收必须可执行

`design.md` 最后一节是「验收」，内容为**能直接执行的命令**及通过时的预期输出：

```
cargo test --locked --all-features --test lexicon_handler <case_name>
# 预期：新增用例全绿，覆盖 <spec 第 X 条验收标准>
```

需要数据库的集成测试先说明依赖的隔离数据条件。
写不出可跑命令的验收标准，退回去写成可验证的，或明确标注「只能人工验收」并给出步骤与判据。

## 5. 确认与交接

展示档位、必要记录与验收方式；仅尚未决定的重大产品或技术取舍需要确认，已有批准沿用。
仅要求评估时交付到此；已要求实施且需求明确时，在当前会话进入 [build](../build/SKILL.md)，不额外要求换会话。
