# 后端评估：查清依赖，留下可实施的方案

通用分档、任务记录与授权遵循 [AGENTS.md](../../../AGENTS.md)。仅评估时不写实现、不跑迁移、不改数据库；原请求包含实施且目标明确时，完成必要评估后在当前会话继续 [build](../build/SKILL.md)。

## 1. 复用基线与记录

- 先读已有任务描述、设计和实际代码；已明确的方案不重新评估，小改动可直接实施。
- 沿 handler → DTO → service → repository → 数据约束查本次相关调用链；涉及 API/DTO 时核对选定前端的实际消费者。
- 查清已在主线、可复用和剩余依赖，只规划剩余关键路径。跨仓共用任务主记录，另一仓引用；分档与文档位置按项目规则，不强制单模块设计文件或双文档。

## 2. 写清本次真正需要的设计

记录目标/范围、现有能力、方案、文件/接口影响、验收与未决问题；只有影响决策时才展开备选方案。

涉及以下变化时保留必要证据：

- **迁移**：up/down、执行顺序、历史数据影响、数据损失与回退限制。
- **契约/权限**：method/path、响应与错误、必填/可选/nullable/枚举、资源授权及消费者影响。
- **配套发布**：使用 [contract-sync](../contract-sync/SKILL.md) 与 [配套发布清单](../contract-sync/references/paired-release.md)，按实际 schema/消费者验证新旧组合后决定顺序；未知兼容性标为待验证，不用「同批发布」代替中间版本验证。

验收写可执行命令及预期；需要数据库时说明隔离条件。只能人工验收的给步骤与判据，不用模糊的“测试通过”代替完成标准。

## 3. 到约定终点

仅尚未决定且影响范围、产品行为或不可逆风险的取舍需要确认，已有授权持续沿用。
仅评估交付必要记录、未决问题与可实施条件；已授权实施就继续 build，不增加确认或交接步骤。
