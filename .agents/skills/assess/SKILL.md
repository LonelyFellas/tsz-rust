# 后端评估：定档 → 调研 → spec → 交接

产出是 spec 和可执行的验收命令，**不写实现代码、不跑迁移、不改数据库**。项目约定读 `AGENTS.md`。

## 1. 先定档

| 档位     | 判据                                                                            | 产出                                        |
| -------- | ------------------------------------------------------------------------------- | ------------------------------------------- |
| **跳过** | 一句话能说清 diff：改日志、重命名、补一条断言、调整错误文案                     | 不写文档，直接进 [build](../build/SKILL.md) |
| **轻档** | 单模块内、不动 DTO / 迁移 / OpenAPI / 权限                                      | 一份 `design.md`，≤80 行                    |
| **重档** | API 契约变更、数据库迁移、跨模块、鉴权/权限、数据约束变化、需要前端配套发布     | `requirements.md` + `design.md`             |

混合按最重的部分定档，定完档说明档位和理由。**改动会被前端看到就是重档**，见第 3 节。

## 2. 建立基线

**调研使用当前宿主可用的只读子代理或隔离检索能力，主上下文只接收结论**；
没有这种能力时严格限定检索范围，不在主上下文里漫游整个 `src/`。

按 handler → DTO → service → repository → 数据约束理清要改的点与调用链波及面，
确认是否需要迁移。涉及 API/DTO 时必须核对前端实际消费者，不能只看本仓。

## 3. spec 必须写清发布顺序

写入 `docs/features/<slug>/`；跨仓功能的 spec 集中在任务主仓，本仓引用即可。
`design.md` 自包含（要改的文件与签名、范围外、方案与被否决方案、风险与回退），
**后端另须写清**：

1. **迁移** —— up/down 成对、执行顺序、历史数据影响、能否回退。
2. **契约影响** —— 哪些 method/path 的形状变了，必填/可选/nullable/枚举变化。
3. **发布顺序** ——
   - **响应新增字段 → 前端先部署**（前端 V3 runtime validator 拒绝未声明字段）。
   - **改必填 / 移除字段 / 收窄枚举 → 后端先部署**。
   - 拿不准写「同批发布」并说明理由，不要赌，也不要凭「新增字段应该安全」下判断。

## 4. 验收必须可执行

`design.md` 最后一节是「验收」，内容为能直接执行的命令及预期输出，例如
`cargo test --locked --all-features --test <target> <case>`。
需要数据库的集成测试先说明依赖的隔离数据条件。
写不出可跑命令的验收标准，退回去写成可验证的，或标注「只能人工验收」并给出步骤与判据。

## 5. 确认与交接

档位、spec、迁移与发布顺序、验收命令一起展示，等用户确认；已有明确批准时沿用授权。
确认后交接给 [build](../build/SKILL.md)，**并建议在新的上下文里开始实现**——
评估阶段积累的上下文对实现是负担。
