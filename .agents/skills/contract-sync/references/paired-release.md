# TSZ 双仓配套发布

仅在 API、运行开关或迁移使前后端需要配套交付时使用。纯单组件改动继续现有 ship/deploy，不强制制造双仓发布。
状态默认留在对话或已有交付记录中，不为每次发布新建仓库文档。

## 确定候选版本

按实际涉及的 web、admin、api 列一张表：组件、候选仓库 SHA、PR/目标分支、契约来源、CI run/attempt、当前部署 manifest、下一步。
准备阶段拿不到线上来源就标为未知；不能把候选版本或历史验收记录填成现网版本。

- 前端改动 PR 进入 main；后端按 feature → dev → main，进入 dev 不等于可部署。
- 两仓 SHA 各自独立。前端还要区分 web/admin 的实际部署版本，只更新一个组件时不能把另一个也记为已发。
- 复用前端 `deploy/provenance.mjs`、后端 `ops/release_artifact_manifest.py` 与 `ops/deployment_manifest.py` 的原生来源证据；不发明第二套 manifest。
- 后端记录新增 migration、必要开关及其默认值；前端记录 build 时生效的代理/功能开关。仅检查本次依赖，不自动开启所有功能。

## 由兼容性决定顺序

用相关契约测试、真实响应或受控混合版本验证填下表；没验证就是未知，不能靠同名字段推测成功。

| 组合                            | 必须证明的行为                                              |
| ------------------------------- | ----------------------------------------------------------- |
| 已部署前端 + 候选 API           | 严格 runtime schema 是否接受新增字段/枚举；旧调用是否仍可用 |
| 候选前端 + 已部署 API           | 缺失字段、旧状态码、未提供端点是否按设计处理                |
| 候选前端 + 候选 API             | 核心用户路径与权限/失败分支是否符合新契约                   |
| 回退组件 + 发布后的 schema/数据 | 旧二进制/前端能否读取已经迁移或写入的数据                   |

若只有一个过渡组合安全，按该方向发布。若两个方向都不安全或关键兼容性未知，先完成必要的兼容补丁、受控验证或已批准的维护方案，不能用「两边快速连发」跳过中间风险。
后端启动会执行 migration；恢复旧二进制不等于恢复数据库。down migration 可能丢数据，不作为默认自动回退方案。

## 执行与恢复

- 先完成已授权的代码、契约、测试和可审查清单；缺少外部动作授权时，此处就是交付终点。沿用会话中已有的同范围授权，不按仓库反复问相同许可。
- 前后端部署分别读取目标 checkout 的 `.agents/skills/deploy/SKILL.md`。后端必须使用项目指定的 `backend_deploy_runner`，不能让普通 agent 冒充；工具不可用就准确报告限制。
- 两仓现有 deploy 均要求 GitHub 当前 main；这份清单不提供任意 SHA 部署能力。等待期间任一 main/CI run/attempt 变化，重新核对候选配对、兼容证据及该仓门禁，再继续；不传不存在的版本参数绕过检查。
- 保持组件级状态：待发布、已写入待验收、已验收、失败或未知。只在该组件 smoke 和 manifest verify 都通过后标为已验收。
- 中途失败立即按对应 runbook 处理，记录已完成部分、实际版本及恢复限制。继续前读取当前 manifest/锁/state；已成功且来源未变的组件复用验收，不盲目重发整组。

最终报告实际部署的版本组合、契约来源、每组件 CI 与验收、尚未完成部分及回退限制。准备完成与发布完成分别陈述。
