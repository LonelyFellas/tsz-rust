# 统一权限系统：产品方案与需求

> 日期：2026-10-01。状态：设计评审稿，第 11 节五项产品边界已确认；未实施、未部署。
> 本文面向产品验收；实现方案、接口草案、兼容与测试见 [design.md](design.md)。两份文档分别承担需求与技术设计，不再另建重复的总览、接口说明或任务清单。

## 1. 推荐结论

采用 **管理员直接授权 + 统一权限目录 + 菜单／操作／数据范围联合校验**。

- 超级管理员可以从管理员列表给一个人配置权限，也可以从权限列表给多个人批量授予或撤销权限。
- 权限按业务模块组织，可以多对多打标签；标签仅用于整理和选择，不自动产生授权。
- 菜单可见性、页面访问、按钮可用性和后端接口使用同一套权限标识及依赖规则。
- C 端沿用用户身份、数据归属和业务关系控制，不照搬管理员的逐人勾选模式。
- 第一版不引入多角色叠加、个人禁止项、动态规则脚本、任意数据范围配置器或外部权限引擎。

现有菜单过滤是为后续权限系统预留的基础，保留并接入真实授权，不推倒重做。

## 2. 已确认的需求

| 编号 | 需求 |
| --- | --- |
| R1 | 系统有稳定、可扩展的权限清单，后续新功能可以继续增加权限项。 |
| R2 | 只有超级管理员负责向普通管理员下发权限。 |
| R3 | 在管理员列表中，可以单独配置某位普通管理员的权限。 |
| R4 | 在权限列表中，可以选择一个或多个权限，批量授予多个普通管理员。 |
| R5 | 支持给多个权限打标签，用于归类和查找。 |
| R6 | 普通编辑与“编辑他人词库”分开；后者依赖前者，未额外授权时只能编辑自己的。 |
| R7 | 编辑不自动包含发布、删除整个资源或转移归属；编辑后保留创建者，并记录实际修改者。 |
| R8 | 登录或恢复会话时加载本人的生效权限；完整目录进入权限管理时按需加载。 |
| R9 | 菜单也需要可分配的权限，登录后根据当前授权显示菜单。 |
| R10 | 权限设计覆盖 admin 与 C 端的衔接；后端通过 HTTP API / JSON 与前端对接。 |

用户已确认上述能力方向，并于 2026-10-01 确认第 11 节五项产品边界采用原推荐值。其余标为“推荐”的细则仍是设计建议；本次确认不构成代码实施或存量授权变更的执行授权。

## 3. 为什么选择这套模型

| 备选 | 优点 | 主要代价 | 结论 |
| --- | --- | --- | --- |
| 直接给管理员授权，支持批量操作 | 对应当前诉求，某个人拥有哪些权限很直观 | 同类岗位后续变更需再次批量操作 | 第一版推荐 |
| 角色打包权限，再叠加个人例外 | 大团队按岗位统一维护方便 | 取消勾选不一定真的撤权，解释和冲突处理复杂 | 目前不引入；确有同岗维护痛点时再评估 |
| 通用策略引擎／可配置条件规则 | 可表达复杂组织与数据关系 | 配置、测试、排错和运维成本高 | 目前没有相应需求，不采用 |

标签不是角色：修改标签关联不会改变任何管理员已获得的权限。以后若引入角色，必须另行确定直接授权与角色授权的关系，不能悄悄把标签改造成角色。

## 4. 权限分成三类，但共用一个目录

### 4.1 页面／查看权限

控制菜单可见、直接 URL 访问以及该业务域的基础读取。例如 `words.access` 控制“智能词库”的入口和授权范围内的基础查看。

推荐一个普通业务页面先用一个 `.access` 权限同时承担页面访问和基础读取，不机械地拆成“显示菜单”“进页面”“看列表”三个开关。敏感字段、原件下载、导出等另设权限。

一个权限可以对应多个相关路由；不是一个按钮、一个 URL 就建立一个权限。纯导航分组不设额外权限，有可访问子菜单时显示，否则整组隐藏。

### 4.2 操作权限

对应真实业务能力，例如创建、编辑、发布、审核、归档。风险不同或职责不同的操作分开；翻页、排序等普通交互不独立授权。

### 4.3 数据范围扩展权限

例如 `words.edit_others` 只扩大编辑对象范围，不独立提供编辑能力，也不扩大发布、归档等其他操作的范围。

一次操作允许执行，需要同时满足：账号有效、具备所需权限、数据范围允许、业务状态允许。管理员有权限也不能跳过业务数据校验。

## 5. 两个授权入口

### 5.1 从管理员列表配置

1. 超级管理员点击目标人员的“配置权限”。
2. 展示按模块分组的权限清单，支持按名称、标识、标签搜索筛选。
3. 已授予项默认勾选，当前实际生效权限可查看。
4. 保存前列出新增、撤销、依赖补充及连带撤销。
5. 提交成功后两个入口同步刷新；失败时不能假装已保存。

推荐新创建的普通管理员默认没有业务权限，只能访问不含业务数据的个人首页、个人设置、改密和退出。停用账号即使保留授权记录，也不能使用任何业务能力。

### 5.2 从权限列表批量配置

1. 选择具体权限，可通过模块、标签筛选后勾选。
2. 点击“批量授予”或“批量撤销”，再选择管理员。
3. 预览每个人实际会增加或失去的权限；不同人员的结果可能不同。
4. 确认后一次提交，返回明确结果。

推荐规则：

- 批量授予只增加选中的权限，保留各人的其他授权。
- 批量撤销只撤销选中的权限及明确确认的依赖项，不全量覆盖。
- 不提供“把所选人员全部替换为这份权限”的默认操作。
- 第一版单次最多 100 位管理员；全部成功或全部失败，不静默部分成功。
- 多页列表的“全选”默认只选当前页；跨页选中的数量始终可见。第一版不提供含义模糊的“选择所有搜索结果”。
- 超级管理员不进入可授权目标名单；普通授权不能改变超级管理员身份。
- 发生并发修改时提示重新加载和预览，不覆盖别人刚保存的配置。

### 5.3 权限依赖

例：编辑他人词条需要同时拥有 `words.access`、`words.edit`、`words.edit_others`。

- 勾选扩展权限时，界面显示所需基础权限，明确说明将一并授予。
- 撤销基础权限时，列出必须一并撤销的依赖权限。
- 后端执行同样的依赖校验，不能只靠界面自动勾选。
- 取消某个上层操作，不自动撤销不再被它使用的基础查看权限；只有明确选择的撤销及其反向依赖才会被移除。

## 6. 标签规则

- 一个权限可有多个标签，一个标签可包含多个权限，也可以跨业务模块。
- 超级管理员可以创建、重命名、删除标签，并批量添加或移除权限的标签关联。
- 删除标签只删除分类及关联，不删除权限，不影响授权。
- 授权时冻结为具体权限标识列表；以后标签增加或移除权限，不追溯影响此前授权。
- “高风险操作”可以是便于查找的标签，但真实安全等级和强制确认要求由系统定义，不能靠标签决定。
- 业务模块和权限本身由开发注册；超级管理员不能仅新增一个名称就创造新的有效权限。

## 7. “编辑他人词库”的边界

### 7.1 当前代码中的对象

当前“智能词库”实际以单词／短语词条为编辑对象，并有共享例句和发布版本；“词表”“自定义词库”中仍有未落地占位入口。因此产品里的“词库”不能直接假定已经是一个有独立所有者的集合实体。

**已确认第一阶段先落到已实现的后台词条编辑。** 未来词库集合、词表成员管理分别注册对应权限，不把不同对象都装进 `words.edit_others`。

### 7.2 编辑范围与约束

- “他人”先指后台业务内容的其他管理员创建者，不默认包括 C 端用户的私人内容。
- “仅编辑自己的”在草稿和已发布词条的后续修订中都适用，不因发布过就自动允许普通管理员编辑他人内容。
- 创建者不随编辑而改变，新增更新者和审计记录用于追溯。
- 编辑共享例句或共享词条本体，需取得对应资源的编辑权限；拥有引用它的内容的编辑权限，不代表能改共享本体。
- 修改引用关系只影响当前对象时，按当前对象的编辑权限处理；真正修改共享本体时，再校验共享资源权限。
- 归属缺失的历史数据不猜测为当前管理员所有，由超级管理员处理或经单独批准修复归属。

已确认第一版不开放普通管理员发布他人的内容、转移归属或永久删除。普通管理员发布、归档、恢复自己的内容仍需各自的独立权限，不因拥有 `edit_others` 自动扩大这些操作的范围。

## 8. 菜单、页面与接口体验

- 当前权限未加载完成时显示加载态；加载失败提供重试，不默认开放全部菜单。
- 首页始终可进入，但只能展示个人信息和有权限的数据，不能泄露全站统计。
- 对无权访问的菜单隐藏入口；直接输入对应网址显示无权限页面，不触发业务数据请求。
- 对页面中没有操作权限的按钮，统一隐藏；若为解释业务状态而禁用，给出明确原因。
- 授权变化后重新计算菜单、路由和当前资源可操作状态，并清除受影响的查询缓存。
- 当前页面权限被撤销时回到安全页面并提示；已输入但未保存的敏感内容不另存为本地草稿。
- 退出或切换账号清空权限和业务缓存，不能沿用上一位管理员的数据。
- 未上线的占位功能不开放授权，不能把“授权成功”当作对应功能已实现。

## 9. C 端范围

C 端采用用户身份／认证状态、资源归属／协作关系、业务状态联合控制。例如用户只能操作自己的认证申请和通知，教师能力取决于认证状态以及相关业务关系。

第一阶段：

1. 核对已有 C 端接口的归属检查，保留 admin 与用户身份域隔离。
2. 为新增或受影响的资源明确可查看、可编辑等动作；复杂资源可随业务响应返回 `allowed_actions` 供 UI 展示。
3. C 端能力仍由后端根据业务规则判断，不把管理员权限清单下发给普通用户。
4. 管理员在 C 端界面进行管理操作，也必须使用管理身份及对应管理接口，不能借普通用户接口绕开规则。

会员权益、组织成员权限、班级协作、客服访问私人内容目前没有完整产品规则，本方案不擅自新增这些业务。

## 10. 安全与生效原则

- 默认拒绝，新增权限不自动授予已有普通管理员。
- 超级管理员隐式拥有当前已注册的后台业务权限，不通过普通勾选授予“超管身份”。
- 超级管理员同样遵守账号状态、强制改密、资源有效状态及数据完整性规则。
- 身份无效与业务无权限要区分；没有操作权限不能误触发“退出登录”。
- 撤权提交后开始授权判断的新请求，按新权限处理；已经完成的操作不会被撤回。
- 发布等敏感写操作在事务内复核权限，与撤权串行化，防止检查后失权仍提交。
- 已经展示或下载的数据无法通过撤权收回；不承诺清除用户已保存的副本。
- 授权、撤销、标签变更和重要业务写操作可追溯到操作者、目标、变更内容、时间和请求标识。

## 11. 已确认的产品边界

用户于 2026-10-01 确认以下五项均采用原推荐值，作为后续实现和验收依据，不再列为待拍板事项。存量管理员初始化确认的是处理原则；具体人员的授权差异仍须在实测、预演后逐人展示并批准，不代表已经批准实际授予或撤销权限。

| 决策点 | 已确认规则 | 影响 |
| --- | --- | --- |
| “他人词库”的实际对象 | 第一阶段是后台词条，不包含 C 端私人词库 | 决定归属校验的位置及隐私边界 |
| 发布后的他人内容 | 仍需 `edit_others` 才可编辑其后续修订 | 替换旧的“发布后不检查创建者”规则 |
| 普通管理员更高风险的范围 | 发布／归档／恢复先限本人内容；发布他人内容、永久删除、转移归属保持超管专属 | 会与旧发布权限的部分能力存在差异 |
| 存量管理员如何初始化 | 仅保留经接口实测核对的现有能力，逐人展示差异并批准；不一律授予新目录全集 | 避免无意扩权，也避免突然阻断现有工作 |
| 撤权后的在途任务 | 敏感写事务复核；长任务执行前及交付结果前复核，已完成副作用不自动回滚 | 需要在实际存在此类任务时接入 |

## 12. 分阶段交付与验收

| 阶段 | 交付内容 | 通过条件 |
| --- | --- | --- |
| A：规则与契约 | 权限目录、依赖、接口及存量能力映射 | 已实现的受保护接口都有明确策略，关键产品边界已批准 |
| B：后端闭环 | 直接授权、标签、审计、版本并发控制、真实接口校验 | 单人／批量授权一致，越权、撤权、并发和回滚测试通过 |
| C：前端闭环 | 管理员配置、批量授权、标签、菜单／路由／按钮联动 | 真后端下完整流程可操作，直接 URL 和跨账号缓存不会绕过 |
| D：存量切换 | 映射预演、新旧组合验证、受控切换 | 没有无意扩权；差异已批准；旧客户端不能绕过新后端 |
| E：持续扩展 | 新功能按同一接入规范注册权限 | 未注册接口默认不放行；新权限不会自动发给普通管理员 |

产品验收必须至少覆盖：有权限成功、无权限直接调用被拒绝、他人 ID 越权被拒绝、批量授予不覆盖原权限、依赖撤销可预览、标签变化不改授权、菜单直链被拦截、撤权后旧会话被拒绝、C 端用户身份不能调用管理接口。

本次仅完成方案与代码现状核实，不包含上述功能实现或运行验收。
