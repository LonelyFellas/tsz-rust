# 统一权限系统：技术设计与落地评估

> 2026-10-01 · 设计评审稿 · 重档评估（鉴权、迁移、API 契约、前后端配套）。
> 产品需求及已确认的五项产品边界见 [requirements.md](requirements.md) 第 11 节。本次只写方案，不实现业务代码、不跑迁移、不提交、不部署。

## 1. 结论与边界

推荐 **直接授权 + 后端静态注册的权限目录 + 数据归属策略**。不引入角色叠加和通用策略引擎；标签仅用于筛选，不参与授权计算。

权限模型分为页面／基础读取、业务操作、数据范围扩展三类，但统一存储授权、统一查验。前端利用权限改善体验，后端对每次请求独立执行最终决策。C 端保留自己的身份与业务关系规则，不复用管理员的身份或授权清单。

本阶段集中在已实现的管理员、用户管理、词条／例句、教师认证和相关配置接口；班级、词表等占位功能不因注册权限而被视为已交付。不增加多租户、组织树、临时授权、复杂条件表达式、WebSocket 或独立授权服务。

## 3. 权限定义与演进

### 3.1 单一目录

在后端新增 `src/admin/permissions/catalog.rs`，静态注册每个真实能力。目录项包含：

- `key`：稳定唯一标识，创建后不随中文名称和标签更改。
- `module_key`、`label`、`description`：模块与可解释的授权效果。
- `kind`：`page`、`action` 或 `scope`。
- `requires`：必须同时具备的基础权限 key；仅开发修改。
- `risk_level`：系统定义的风险级别，不受标签增删影响。

页面路径、图标和 React 组件仍在前端；后端只提供权限定义和当前授权，不下发可执行路由代码。数据库保存“谁被授予什么”和标签，不维护另一份可任意编辑的业务规则。

权限依赖必须是无环图；启动／单元测试验证唯一 key、依赖存在、无环。目录计算一个 `catalog_version`，当 key、依赖、状态或安全语义变化时更新，用于阻止过期授权预览继续提交。仅调整标签不改变授权目录版本。

只返回本版本已实现、可分配的权限。普通管理员无通配符授权；以后新增 key 不自动加入其授权。停用 key 时先停止使用并完成数据迁移，未知／废弃 key 不生效，不能错误映射到新权限。

### 3.2 首批目录草案

下面是已实现业务的候选拆分，不是声称全部已实现。精确清单由实施阶段的逐接口映射确定，不能遗漏辅助接口。

| 模块 | 页面／基础读取 | 候选操作及范围权限 |
| --- | --- | --- |
| 智能词库 | 保留 `words.access` | `words.create`、`words.edit`、`words.edit_others`、`words.publish`、`words.archive`、`words.restore`、`words.rollback` |
| 多维例句 | 保留 `sentences.access` | `sentences.create`、`sentences.edit`、`sentences.edit_others`、`sentences.publish`、`sentences.withdraw`、`sentences.restore`、`sentences.rollback` |
| 用户管理 | 保留 `users.access` | `users.edit`、`users.set_status`；若返回敏感信息，另定义 `users.read_sensitive` |
| 教师认证 | 保留 `teacherapply.access` | `teacherapply.review`、`teacherapply.revoke`；敏感附件读取另定权限／受控接口，不隐含在普通列表读取中 |
| 词性／形态配置 | 新增 `lexicon_settings.access` | `lexicon_settings.edit` |
| 语音生成 | 按现有实际入口关联词条页面或独立入口 | 生成等会消耗服务资源的操作单独判断，例如 `speech.generate`，不因是预览就全员放行 |

管理员账号治理、权限授权、标签管理、审计检索在第一版保持超级管理员专属，不建立可委派的 `super_admin` 或 `permissions.grant` 开关。个人首页、个人偏好、改密、退出不是可收回的业务权限，但仍需相应有效会话／恢复流程。

### 3.3 依赖与归属

推荐 `words.edit_others → words.edit → words.access`；创建、发布、归档等依赖对应 `.access`，发布不依赖编辑，允许编辑与审核发布分工。

一次授权后，存储集必须已满足依赖：授予扩展权限时显式补齐并预览，撤销基础权限时显式展开反向依赖。不要只在读取时偷偷补权限，否则数据库、界面和审计会不一致。

编辑、发布、归档的范围分别判断，不能把 `edit_others` 当成“可操作一切他人内容”。后台词条范围、已发布内容的编辑限制，以及发布／归档／恢复等边界已按需求文档第 11 节确认；下表中的回滚本人限制仍为细分设计建议。存量账号的具体能力映射另行预演并批准。

| 动作 | 普通管理员 | 超级管理员 |
| --- | --- | --- |
| 查看后台业务词条 | 有 `words.access` 后读取该后台域允许读取的数据 | 后台业务域内允许，不据此取得 C 端私人内容访问权 |
| 编辑本人词条 | `words.edit`，且归属本人、状态可编辑 | 仍遵守状态和数据约束 |
| 编辑他人词条 | 同时具备 `words.edit_others`，草稿和已发布后的修订都检查 | 后台业务域内允许，仍遵守状态和数据约束 |
| 发布、归档、恢复、回滚 | 各自权限，并限本人内容 | 后台业务域内允许，仍遵守状态和数据约束 |
| 永久删除、转移归属 | 第一版不开放普通授权 | 如现有业务支持，继续按专属流程；本方案不新增对应业务功能 |

不能通过把 `is_super_admin` 改成“超管或有编辑他人权限”来复用旧函数；这会让一个范围权限获得超管在其他业务中的豁免。

## 4. 后端执行模型

### 4.1 请求级上下文

建议引入请求级 `AdminAuthorization`，包含当前管理员身份、最新账号状态、超级管理员身份、授权版本和有效权限集合。

拟定的核心职责／签名：

- `load_admin_authorization(state, auth) -> Result<AdminAuthorization, AppError>`：复用有效身份、停用、强制改密校验，每次请求从可信数据库读取当前授权。
- `require_permissions(ctx, required: &[PermissionKey]) -> Result<(), AppError>`：已注册权限的集合校验。
- `require_entry_action(ctx, entry, action: EntryAction) -> Result<(), AppError>`：结合资源归属、发布状态及具体动作判断。
- `preview_change(current, grant, revoke) -> Result<PermissionChangePreview, AppError>`：单人和批量共用的依赖与差异计算。

以上为拟新增接口，不是当前已经存在的函数签名。鉴权上下文不得由客户端 JSON 直接反序列化得到。

### 4.2 路由与数据层职责

1. 管理身份校验保留现有 admin realm；C 端用户 token 不能进入管理接口。
2. 对每个受保护 method/path 标明：基础会话、超管专属、或具体业务权限；不再以 GET／POST 默认推断授权。
3. 业务权限在 handler／中间件检查；数据归属和状态在 service／repository 事务中执行，覆盖所有调用入口。
4. 详情、列表、分页总数、搜索、导出、附件下载、批量操作均受相同数据范围约束。需要限制范围时，在 SQL 查询及计数阶段限制，不能查询全部再由前端过滤。
5. 创建者和操作者取自认证上下文；忽略或拒绝客户端试图指定创建者的字段。
6. 批量业务操作逐对象检查；不能只检查第一个对象，也不能通过更换 ID、嵌套资源 ID 或批量入口绕过。
7. 默认未声明策略的受保护业务路由不放行；公共登录、验证码和会话恢复等需明确列为不同策略，而不是一律套业务权限。

按已导出的 OpenAPI 建立路由策略覆盖测试，并与实际路由注册对照，覆盖只在内部注册、未出现在 spec 的入口。该映射保留在代码／测试中，不再手工维护另一份逐路由文档。

### 4.3 超管与 C 端

超管身份来自当次可信查询，而非仅相信旧 token 的 role claim。超管可以通过已注册后台权限检查，不意味着跳过强制改密、停用、状态约束或跨身份域限制。

C 端继续由用户认证、认证资格和资源关系派生动作。若需要给 UI 返回 `allowed_actions`，在真实业务响应中按当前资源计算；不传管理员目录、不接受客户端提交的动作列表作为证据。用户本人资源查询必须绑定认证 subject，不能相信传入的 `user_id`。

## 5. 数据模型与审计

| 数据 | 主要字段／约束 | 用途 |
| --- | --- | --- |
| `admins.permission_version` | 非空、初值 0、仅真实授权变更时递增 | 乐观并发控制；不同于登录／会话安全版本 |
| `admin_permission_grants` | `admin_id`、`permission_key` 联合主键；`granted_by`、`granted_at`；按 permission_key 建检索索引 | 直接授权，不存角色、允许／禁止混合项 |
| `permission_tags` | UUID、唯一规范化名称、创建／更新时间、非空 `version`（初值 0） | 标签管理及并发控制，不含授权规则 |
| `permission_tag_items` | `tag_id`、`permission_key` 联合主键 | 标签与权限多对多 |
| 既有 `audit.admin_actions` | 复用 actor、action、resource、request_id、metadata | 授权、撤销、标签、重要操作的追溯 |

权限定义来自注册表，因此 `permission_key` 暂不对另一张目录表建立外键；写入必须经过注册表校验，历史未知值不生效并告警。依赖闭合和目录检查由后端及测试保证，不宣称普通数据库约束能完成全部验证。

标签关联对标签设置外键；管理员授权对目标管理员设置外键。删除／停用管理员沿用现有账号治理流程，不为了本功能新增硬删除能力。审计身份留存不能因账号移除而级联丢失。

授权事务同时写入具体 before／after、实际新增／撤销、目标管理员、授权版本、目录版本、操作者和请求标识；同一批次用请求标识关联各目标记录。审计写入失败则授权事务失败。无实际变化的重放不递增版本、不重复生成“已变更”记录。

标签变更也审计，但不能伪造为授权变更。重命名和关联集合真实变化时递增对应标签的 version；批量标签操作在同一事务中锁定并检查全部目标标签，冲突时整体回滚，不改变任何管理员的 permission_version。敏感业务审计记录动作和必要差异，不复制密码、token、完整认证原件等敏感内容。

## 6. HTTP / JSON 契约草案

以下路径相对 `/api/v1`，是建议契约，不是当前可调用接口。正式实现时以 Rust DTO 和导出的 OpenAPI 为准，前端保持 snake_case。

### 6.1 接口清单

| 接口 | 调用者 | 语义 |
| --- | --- | --- |
| `GET /admin/profile` | 当前管理员 | 现有身份信息 + 本人生效权限与版本 |
| `GET /admin/permissions` | 超管 | 完整可分配目录、目录版本，结合标签关联展示 |
| `GET /admin/admins/{admin_id}/permissions` | 超管 | 指定普通管理员的权限与版本 |
| `GET /admin/permissions/{permission_key}/admins` | 超管 | 分页查看拥有该具体权限的普通管理员；隐式全权的超管单独说明 |
| `POST /admin/permission-changes/preview` | 超管 | 对所选人员展开新增／撤销及依赖，返回逐人差异，不落库 |
| `POST /admin/permission-changes` | 超管 | 提交精确变更与预期版本；单人和批量使用同一契约 |
| `GET /admin/permission-audits` | 超管 | 按人员、权限、时间分页检索授权与标签变更记录，复用既有审计数据 |
| `GET /admin/permission-tags` | 超管 | 获取标签及关联信息 |
| `POST /admin/permission-tags` | 超管 | 创建标签 |
| `PATCH /admin/permission-tags/{tag_id}` | 超管 | 重命名标签，带标签版本条件防止覆盖 |
| `DELETE /admin/permission-tags/{tag_id}` | 超管 | 删除标签及关联，带版本条件，不影响授权 |
| `POST /admin/permission-tag-changes` | 超管 | 对多个权限、多个标签增删关联；显式 add/remove，受影响标签版本一并检查 |

不需要为“从人授权”和“从权限授权”建立两份存储或两套执行逻辑。目标不存在、目标为超管、未知权限、依赖不满足、超出批量上限，均整体拒绝并返回可定位的错误。

### 6.2 Profile

保留现有 `id`、`phone`、`display_name`、`role`、`preferences`。`role` 已能表示超管，不再新增重复的 `is_super_admin` 字段。

新契约下 `permissions` 始终是非 null 的字符串数组，表示本人全部有效权限，而非全系统菜单目录；增加必填 `permission_version` 与 `catalog_version`。空数组表示没有业务授权。普通账号禁用／强制改密继续按现有专用错误契约处理。

示意片段（不是省略字段后的完整 wire response）：

```json
{
  "role": "admin",
  "permissions": ["words.access", "words.edit", "words.edit_others"],
  "permission_version": 12,
  "catalog_version": "catalog-v1"
}
```

`catalog-v1` 仅作说明，实施使用注册表生成的稳定版本。权限 key 的 wire 类型允许字符串；后端提交校验严格拒绝未注册 key，前端未知 key 不会匹配任何本地路由／按钮，不能推断通配符授权。保持已存在的菜单 key，不进行无意义重命名。

超管 profile 可返回注册表全集供 UI 统一使用；后端仍按真实超管身份校验，不在数据库给每个超管插入全量授权行。

### 6.3 预览与提交

预览请求包含 `catalog_version`、目标管理员，以及此次共同选择的 `grant`、`revoke`。单人配置已读取旧快照时，必须带打开配置时的 `expected_version`；从权限列表首次选择一批人员时，可由后端在一次批量查询中取得当前版本，无需逐人发请求。预览响应返回每人的 before／after、精确 grant／revoke、依赖原因和用于提交的 expected_version。最终提交时每个目标的版本必填。

提交接受预览得到的逐人明确变更。例如：

```json
{
  "catalog_version": "catalog-v1",
  "targets": [
    {
      "admin_id": "11111111-1111-4111-8111-111111111111",
      "expected_version": 7,
      "grant": ["words.access", "words.edit", "words.edit_others"],
      "revoke": []
    },
    {
      "admin_id": "22222222-2222-4222-8222-222222222222",
      "expected_version": 4,
      "grant": ["words.edit_others"],
      "revoke": []
    }
  ]
}
```

示例假定第二位管理员已经有基础访问和编辑权限。后端重新读取并校验，不相信预览或浏览器状态。提交后应返回各目标最终权限、最新版本和请求标识。

同一 key 同时出现在 grant/revoke、重复目标或超过 100 个目标按参数错误拒绝。预览后修改人员／权限选择，前端必须使预览失效。目录变化或任一人员版本变化返回冲突，整批不变更。

不存长期预览任务，不引入复杂分布式批处理。客户端遇到网络超时先回读状态再决定重试；不能把超时视为一定失败。重复有效的增加／移除具有集合幂等性，但旧 expected_version 可能返回 409，不能承诺盲目重试仍然成功。

### 6.4 错误语义

| 状态码 | 语义与前端处理 |
| --- | --- |
| 401 | 认证无效，进入现有会话恢复／登录流程 |
| 403 | 权限不足或当前账号状态不允许；用业务 code 区分撤权、停用、强制改密，不一律登出 |
| 404 | 资源不存在；对不应暴露存在性的跨用户私有资源，也使用相同不存在语义 |
| 409 | 授权版本、目录版本或资源版本冲突，重新读取并预览，不覆盖保存 |
| 422 | 请求字段、未知权限、依赖组合或批量上限不合法 |

错误体复用项目现有 Problem Details / 业务 code 形式，不新建第二种错误信封。普通调用者的错误不泄露其他管理员的权限或私有资源信息。

### 6.5 旧发布布尔字段

`can_publish_lexicon` 目前包含词条和例句发布、生命周期等多种能力，不能直接当作一个新 key 的无损别名。

过渡策略：保留响应字段一段兼容期，但由新授权计算，仅在完整具备已核实的旧能力包时为 true；不能继续让旧布尔列成为独立授权来源。新前端不再依靠该字段决策。

旧 `PATCH /admin/admins/{admin_id}/lexicon-publication-permission` 在新模型激活后拒绝变更并返回明确升级提示，要求使用新授权接口；不允许旧入口绕过版本、依赖和审计。若必须兼容旧入口，需另行实现映射到同一变更服务的适配器并验收，不能默认获得这一兼容承诺。

旧前端不能完整表达细粒度权限，也可能把兼容布尔值理解得过宽，故不将其与新后端的组合声明为完整功能兼容；后端必须始终保证拒绝越权。

## 7. 前端接入与缓存

### 7.1 加载与存储

- 继续 login / refresh 后请求 profile，不把完整权限目录塞进登录响应或长期 token。
- 在 `@tsz/shared/auth` 维护当前管理员、权限集合与加载状态；一个请求响应可供多个页面共用，不给每个按钮发请求。
- 权限信息以当前会话内存为主，不把 localStorage 中的旧授权当成放行依据。
- 目录、标签、其他管理员授权只在超管管理页按需请求；人员列表和某权限的授权人员列表分页。
- 窗口重新聚焦、恢复会话及业务权限 403 后按需刷新 profile，合并并发刷新；不使用短间隔轮询或 WebSocket。
- 标签仅改变筛选。批量提交发送具体 key，不能只发标签 ID 让后端按后来变化的标签集合授权。

### 7.2 菜单／路由／按钮

抽取共用的页面权限元信息，菜单和路由读取同一映射，避免一个已隐藏另一个仍可进入。直接 URL 的路由检查必须在页面业务查询发出前执行。

保留 `.access` 的基础读取语义；垃圾桶等子页面若需要区别可见性，可使用同模块额外的只读 key，不把“恢复操作权限”误用为全部垃圾桶读取权限。

操作按钮读取具体权限；复杂资源基于归属和状态做保守判断，或由业务接口返回 `allowed_actions`。新增该字段前先更新严格 runtime schema 并验证旧消费者，不能未经验证向所有 V3 响应追加字段。

当前页面失权时卸载受保护内容、取消相关查询、清除受影响的 TanStack Query 缓存，再进入无权限／安全首页。业务缓存按 admin identity 隔离，登出和账号切换全部清理。不可把一次资源状态冲突误当作全局撤权。

### 7.3 页面落点

管理员列表增加“配置权限”入口；新建“权限管理”页面，集中承载目录、按权限查看人员、批量授予／撤销及标签。标签不再独立开一套多级页面。

现有 `features/roles` 的筛选和勾选交互可择需复用；角色绑定／系统角色数据模型不沿用。只清理本次替换导致的失效路由和引用，不顺手删除所有历史角色代码。

## 8. 并发、生效与性能

### 8.1 授权事务

1. 开启事务，按确定的管理员 ID 顺序锁定操作者及目标行，避免不同批次相互倒序锁定。
2. 在锁内确认操作者仍为有效超管、目标均为允许配置的普通管理员。
3. 核对 catalog_version 和每个 expected_version，任何不符均整体回滚。
4. 验证最终集合依赖闭合；写入授权、递增有实际变化的版本、插入审计。
5. 提交并返回最终状态。操作中没有外部网络调用。

单次有界批量足以满足当前需求，暂不加异步任务队列或逐人最终一致机制。

### 8.2 撤权的时间边界

第一版有效授权从 PostgreSQL 读取，请求内复用，不增加跨请求 Redis 权限缓存。一个列表响应只加载一次权限上下文，不逐条资源查询权限，避免 N+1。

一般读取请求以执行授权查询的时刻为判断点；撤权提交后开始判断的请求不能沿用旧缓存。已经通过检查的在途读取可能完成，已展示内容无法收回。

发布、归档、授权等敏感写操作在业务事务中重新加载并锁定当前操作者授权，沿用现有发布与撤权共用管理员行锁的方向。全局锁顺序统一为管理员授权行再到业务对象；实施时检查现有流程，不能制造相反顺序。若业务先取得共享锁并提交，撤权在其后生效；若撤权先提交，业务按新权限拒绝。

如果后续存在长任务，至少在执行副作用前及交付受保护结果前复核；本次不凭空建设不存在的任务系统。

### 8.3 性能选择

目录通常只有几十至几百项，使用代码内常量；个人授权按主键索引读取并转为集合。人员和审计分页，关联查询有索引。未测量前不引入分布式缓存；以后确有瓶颈，再设计版本化缓存与失效传播，不能降低撤权保证。

## 9. 迁移、存量映射与兼容发布

### 9.1 数据迁移

按实施时最新时间戳新增成对 up/down，先增加授权／标签表、索引和 permission_version，不修改现有会话安全版本，不删除旧发布列。

存量授权另做可预演的数据迁移步骤：

- 从实际接口政策和隔离测试得出旧有效能力，不按 profile 的固定 12 个菜单 key 全量回填。
- 当前普通管理员能读哪些业务，需要逐组核实；用户管理、教师认证等原有超管专属内容不能因为菜单曾显示就授予普通管理员。
- `can_publish_lexicon=true` 的现有能力拆包，明确发布、归档、恢复、回滚和归属范围的对应差异。
- 新的编辑与编辑他人权限默认不自动授予，不将“拥有旧发布权限”推导成“拥有编辑权限”。
- 生成逐人 before／after 差异，实际授权范围变化须经产品批准。没有现网数据和批准映射前，不能写死一条 `INSERT ... SELECT 全部管理员×全部权限`。
- 历史数据转换可重入，记录迁移来源；真正切换后不再根据旧布尔列反向覆盖新授权。

新账号默认零业务权限。迁移后对授权集合做目录有效性和依赖闭合校验，抽样核对账号数、旧能力映射与预期差异。

### 9.2 四种组合必须实测

| 组合 | 必须验证的行为 | 当前状态 |
| --- | --- | --- |
| 旧前端 + 新后端 | 新 profile 字段／权限 key、旧发布字段、旧授权入口、V3 严格解析；旧 UI 不得绕过新后端 | 未验证；不宣称完整可用 |
| 新前端 + 旧后端 | 缺少版本字段或新接口时明确显示升级／不可用，不能把固定菜单清单当成新模型的授权 | 未验证；必须失败关闭新授权功能 |
| 新前端 + 新后端 | 菜单、业务操作、归属、批量、标签、撤权和错误处理闭环 | 未验证 |
| 回退组件 + 已迁移数据 | 旧代码是否忽略细粒度权限、是否重新放宽 GET 或恢复旧发布布尔值 | 存在安全风险，不能默认回退 |

### 9.3 推荐发布顺序

本方案不假定增加 JSON 字段天然兼容，也不靠“两边一起发布”规避中间版本。

1. 完成纯增量 schema 准备及迁移预演，旧行为暂不改变；确认旧二进制能接受新增表／列。
2. 在隔离环境验证上表，以及来源明确的 admin / web / API 版本配对、OpenAPI 和生成快照。
3. 若能证明安全且可用的过渡方向，按已验证方向发布；否则推荐经过批准的短维护窗口，暂停后台业务访问与写入，并等待在途敏感操作完成。
4. 在保护期间执行已批准的数据映射，切换到强制校验的新后端，再更新匹配的新 admin 前端，完成冒烟后恢复后台访问。若共享后端重启影响 C 端，也须明确窗口与验证范围，不能假定 C 端零影响。
5. 不混跑仍会绕过新策略的旧后端副本；刷新页面不能代替替换旧实例。遗留浏览器客户端仍应由新后端拒绝未授权请求。
6. 兼容期结束且旧消费者退出后，再另行迁移删除旧布尔字段和废弃接口。

具体执行服从现有 ship/deploy、CI、制品来源和后端部署代理规范；本任务不包含这些外部操作授权。

### 9.4 回退边界

新增 schema 的 down 可以在没有真实授权／标签数据、且新模型未启用时经验证撤回；写入真实数据后直接 drop 会丢失授权和标签，不属于默认可回滚操作。

**启用细粒度控制后不能直接恢复现有旧后端对 GET 的广泛放行策略。** 首选保留新 schema 与授权数据、前向修复；必要时保持后台维护／拒绝状态。只有已证明保留权限隔离的兼容版本可作为二进制回退目标。旧布尔列仅可作为历史对照，不能用来重建新授权事实。
