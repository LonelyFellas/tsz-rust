# 变化组独立英美配置，并支持「专用于某个词义」

状态：**后端实施中**（未决问题全部采纳建议）。评估基线 tsz `0bf39b2`、tsz-rust `origin/main 3932435`（2026-09-13）。
禅道 [TASK#45](http://47.121.142.19/zentao/index.php?m=task&f=view&taskID=45)，创建者杨老师，指派余胜明。
按杨老师口径**算新增功能核算工时**，且**不考虑已有词条的兼容**（测试服清库重来）。

## 背景

job /dʒɒb/ 下有一个特例词义 Job /dʒəʊb/：大写、读音不同。杨老师希望在第 2 步「词形与发音」
里给它单独建第 2 组词形与发音，然后把第 1 组标成「通用」、第 2 组标成「专用」（专用于 Job 这项词义）。

截图里被拦的现象：第 1 组 job 英美音标不同，在第 2 组把「英美音标是否有区别」改成「否」时弹出
「暂不能合并英美配置」。原因不是 bug，而是**英美配置现在挂在词性上**（`WordPosFormsV3.dialect_rules`），
组卡片里的开关改的是整个词性，页面也写明「在任一变化组内修改都会同步到本词性的全部变化组」。
第 2 组一改，第 1 组也得跟着合并，第 1 组合并不了，就整体拒绝。

所以这条需求实际是两件事：

1. 英美配置从词性下沉到变化组，组与组互不影响；
2. 变化组分「通用 / 专用」，专用组绑定到具体词义。第 2 件目前完全没有——词义只按词性归属，
   后端 DTO 注释也写着「Phase 1 sense 仍只按 pos_id 归属」。

## 目标端

- admin V3 词条编辑器（第 2 步词形与发音、第 3 步词义与例句、第 4 步预览校验定位）；
- tsz-rust V3 契约、存储、校验、发布快照、词条列表方言列。
- **C 端 web 不在本期**：web 目前不读词形数据；将来展示词义时按绑定选组，另起任务。

## 需求

1. 每个变化组自带 `dialect_rules`（拼写 / 音标是否区分英美），组内词形按本组规则校验；
   词性上不再有 `dialect_rules`。合法组合沿用现状：unified/unified、unified/distinguish、
   distinguish/distinguish（拼写区分则音标必区分）。
2. 一个词形只属于一个变化组。现有契约允许跨组共用词形，但界面从未提供过入口（`addMembership`
   无任何调用方），收紧后组级规则才没有「共用词形听谁的」问题。
3. 变化组带 `scope`：`general`（通用）/ `dedicated`（专用）。新建组默认通用。
4. 词义可选绑定一个专用组（`form_group_id`）：绑了就用那组的词形与发音；不绑就用本词性的通用组。
   只能绑同一词性下的专用组。
5. 完成 / 发布时：
   - 专用组至少被一个词义绑定（否则它对任何词义都不可见，是死数据）；
   - 没绑定的词义所在词性至少要有一个通用组；
   - 每组仍要求至少一个原形（现有规则不变）。
   草稿态不卡这两条，只卡结构性错误（绑定指向不存在 / 非专用 / 跨词性的组）。
6. 第 2 步删掉或把专用组改回通用时，已绑定它的词义自动改回通用，且必须经现有「词形影响预览」
   列出受影响词义并确认后才保存。
7. 第 1 步「是否区分英美」的选择继续决定新建词条初始组的英美配置；之后各组各改各的。
8. 词条列表的「方言」列改为按该词条所有变化组的拼写模式聚合（任一组区分 → 英/美，否则通用）。

## 范围与不做

- 做：上述 1–8，前后端同批。
- 不做：C 端展示；发布快照里的历史数据迁移；例句 / 关联词 / 短语成分引用的组一致性校验（见未决 4）。
- 撤销一条旧决定：`tsz-rust/docs/features/smart-lexicon-v3-step2-form-types/requirements.md` 2026-08-27「地区模式按 POS 统一」
  与「同一 form 可被多个 group 共享」两条，本任务反转，文档一并更新（design §11）。

## 约束

- **无兼容承诺**：词性上的两列直接删、组上直接加非空列；`entry_editor_projection` JSON 与发布快照
  不回填。测试服按既定口径清库（`TRUNCATE lexicon.*` + 两张词性表，`dictionary` / `metadata` 不动）。
- **前后端同批部署**：响应新增字段（组的 `scope` / `dialect_rules`、词义的 `form_group_id`）在前端
  strict runtime schema 下要求前端先；请求删除词性 `dialect_rules` 在后端 `deny_unknown_fields` 下
  要求后端先。两头都有，只能同批 + 清库。
- 节点 ID 绑定不变量不动：组切换英美模式时变体 ID 继续走 `createStableVariantIdFactory`，
  换槽位后端仍 422。

## 验收标准

- [ ] job 案例：第 1 组 uk/us 音标不同，第 2 组独立设为「不区分」，保存成功；第 1 组不受影响。
- [ ] 第 2 组标为专用、第 3 步 Job 词义绑定第 2 组，完成校验通过，发布成功，
      发布快照里词义带 `form_group_id`、组带 `scope` 与 `dialect_rules`。
- [ ] 专用组无词义绑定 → 完成校验报错并定位到该组卡片；未绑定词义且词性无通用组 → 定位到该词义。
- [ ] 删除已被绑定的专用组 → 影响预览列出受影响词义，确认后词义回到通用。
- [ ] 同一词形出现在两个组 → 保存 422 `form_group_membership_invalid`。
- [ ] 词条列表方言列：任一组区分拼写显示英 / 美，否则通用。
- [ ] 前端 `sync:openapi` 后契约测试与 runtime schema 测试绿；admin e2e `admin-word-v3.spec.ts`
      第 2 步保存 payload 断言更新后绿。

## 未决问题（会上定）

每条都给了建议，方便直接拍板。

1. **通用 / 专用要不要在第 2 步显式标？** 另一种做法是不加 `scope`，只看第 3 步有没有词义绑定它。
   建议**显式标**：管理员在第 2 步建 Job 组时意图就已明确；不显式标就没法校验「专用组必须被绑定」，
   也没法在第 2 步提示「此组已绑定 N 个词义」。
2. **一个专用组能否给多个词义共用？** 建议**允许**——多义同读音的特例（如同一个大写专名的几个义项）
   不必重复录一组。
3. **一个词性能否有多个通用组？** 现在允许（dreamed / dreamt 两套变化），建议**保留**。
4. **专用组的词形被例句 / 关联词 / 短语成分引用时，是否校验引用方词义与组匹配？**
   引用目前落到具体词形与英美侧（`target_form_id` / `target_variant_id` + `target_sense_id`）。
   建议**本期不校验**：先把结构做出来，等 C 端接展示时看是否真会出现错配再补。
5. **语法结构的英美形态跟哪个组走？** 语法结构挂在词性上，不分组。建议**词性内任一组区分拼写就出
   英 / 美两条**（与列表方言列同口径）；后端校验本来按第 1 步 headwords 放行两种形态，不用动。
6. **绑定选择器放哪？** 建议放在第 3 步词义卡片上、只在本词性存在专用组时出现，选项标成
   「第 N 组 · Job」；第 2 步不反向选词义（第 2 步保存时词义可能还没建）。
